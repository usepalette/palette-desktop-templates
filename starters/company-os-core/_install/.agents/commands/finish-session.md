# Finish session

The wrap-up at the end of a session that someone will want to come back to. Skip it for a quick fix or a one-file edit.

Say "let's wrap up", or name the command.

## 1. Look at what was done

Go through the conversation and the files that were created or changed. Read what you don't recognise, so the wrap-up describes the work and not just file names.

## 2. Leave things in order

Do the ones that apply:

- **Drafted content** follows [page states](../page-states.md). Say which named pages or sections await review; direct factual corrections and navigation updates need no repeated approval.
- **Lists.** A new person, space, customer, project, product or competitor has its row. A project or a customer that changed state says so in its row.
- **Customer or project.** If the session was about one, refresh its "Now" line. A customer also gets a dated Activity line; a project gets a `Decision:` line only if something was decided.
- **Scratchpad.** Every new item has its line in the scratchpad's `README.md`. Remove only disposable copies created in this session and within the authorized scope; preserve pre-existing work.
- **Follow-ups.** Use the one task home named in `company/tools.md`: the tracker or the shared fallback when no tracker is used. A log line is history, not a substitute for an open task. Say when a task could not be filed.

## 3. Memory lines

Write safe, authorized lines capturing what the person stated. Propose new rules, sensitive choices and changes outside their authority; do not request approval again for an already approved batch:

- What to do differently next time → the nearest relevant existing `lessons.md`: the rule first, two sentences at most.
- What happened or was decided → the nearest relevant existing `log.md`; a real decision starts with `Decision:`.

Use the narrowest place that benefits: the person, then the folder, then the whole workspace. If the correction is about a fact or a format that has its own page, fix the page instead.

## 4. Say what you did

In a few lines: what was done, which pages are waiting to be confirmed, which memory lines were added and where, and what is left for next time. Mention a host-specific save or sharing step only when the host's actual behavior is known. Do not invent whether a file is already shared.
